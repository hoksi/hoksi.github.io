개인 토이 서버에서 2주 동안 Claude Code를 "설계자이자 검토자"로, OpenCode(무료 모델)를 "일꾼"으로 나눠 써 봤습니다. 비싼 모델의 토큰을 아끼려고 시작했는데, 해 보니 **무엇을 맡기느냐보다 검토 비용을 어떻게 줄이느냐**가 더 중요했습니다. 실제로 돌려 본 사례와 숫자를 정리합니다.

## 구조: 설계는 Claude, 실행은 OpenCode

```
Claude Code ── 명세·테스트 작성, 결과 검증, 서비스 연결
     │  oc-delegate (셸 래퍼)
     ▼
OpenCode (무료 모델) ── 코딩, 로그·DB 분석, 대용량 결과 읽기 → 25줄 보고서
```

위임은 셸 래퍼 하나로 감쌌습니다. 모드는 세 가지입니다.

* **코딩:** 고정된(잠긴) 테스트를 통과할 때까지 구현합니다.
* **운영·분석:** 기존 폴더에서 셸을 써서 조사하고 짧게 보고합니다.
* **후속:** 같은 세션을 이어서 지시합니다.

실행이 끝나면 `== RESULT name=fx-api mode=code calls=1 secs=133 tests=PASS tampered=no` 같은 한 줄만 남습니다. Claude는 이 줄과 짧은 보고서만 읽습니다.

## 측정: 같은 작업을 직접 vs 위임

간단한 프로토콜 엔진(GTP) 구현을 두 세션에서 따로 해 봤습니다.

| | Claude 직접 | OpenCode 위임 |
| --- | --- | --- |
| 비용 | $0.43 | $0.30 (−30%) |
| 시간 | 2분 35초 | 8분 5초 |
| 코드 품질 | 짧고 일관됨 | 중복 로직, 상태 오염 경로 |

30%를 아꼈지만, 위임한 코드를 리뷰하느라 그 절약분의 상당 부분을 다시 썼습니다. **작은 작업은 직접 하는 편이 낫다**는 것이 첫 교훈이었습니다.

## 잘 된 것: "많이 읽고 짧게 보고"

위임 효과가 가장 컸던 건 **읽을 양이 많은 일**이었습니다.

* **실행 기록 감사:** 과거 위임 기록 14개를 읽고 테스트 오류 사례 6건을 분류하는 데 44초 걸렸습니다.
* **리버스 엔지니어링 결과 분석:** 분석 도구가 만든 657MB짜리 결과를 OpenCode가 읽고, Claude는 25줄 보고서만 받았습니다.
* **테스트가 고정된 코드:** REST API 모듈(197줄)은 테스트 17개를 한 번에 통과했고, 133초 걸렸습니다.

비싼 모델은 대화가 길어질수록 매 호출마다 전체 문맥을 다시 읽습니다. 큰 출력을 읽는 일을 밖으로 빼는 것이 토큰 절약의 핵심이었습니다.

## 조심할 것: 테스트, 품질, 지시 위반

**1. 테스트를 OpenCode가 쓰면 검토가 필수입니다.** 이번 REST API 테스트에서만 버그 3건이 나왔습니다.

* 테스트 실행기가 함수 목록을 `sorted()`로 정렬하다 `TypeError`로 죽어서, **아무 테스트도 실행되지 않았습니다.**
* 확신도 0.12인 항목이 0.75 필터를 통과한다고 기대했습니다.
* 같은 초에 저장된 두 기록의 순서에 의존해서 결과가 흔들렸습니다.

해결 방법은 단순합니다. assert만 보지 말고 **테스트의 보조 코드까지 읽고**, 잠그기 전에 **빈 모듈로 한 번 돌려 봅니다.** 모든 테스트가 "실패"로 정상 기록되면 실행기는 건강한 것입니다.

**2. 품질은 명세로 지킵니다.** 명세에 "품질 제약" 섹션을 고정으로 넣었습니다. 같은 로직은 한 함수로, 넓은 `except`는 최상위에서만, 상태 변경은 복사본에서 시험한 뒤 반영하라는 식입니다. 구조를 잡는 30~50줄 뼈대는 Claude가 직접 쓰는 편이 가장 안정적이었습니다.

**3. 보고서만 믿지 않습니다.** "이 도구만 쓰라"고 했는데 OpenCode가 브라우저 캐시를 직접 꺼내 우회한 적이 있습니다. 답은 맞았지만 보고서에는 드러나지 않았습니다. 지금은 모든 위임에 **발견마다 출처 표시**(`source=도구 / source=own`)를 요구하고, 실행 기록에서 금지 경로만 grep으로 확인합니다.

## 보안: 무료 모델은 받은 것을 학습에 씁니다

무료 등급 모델은 보낸 내용을 학습에 쓸 수 있습니다. 그래서 세 겹으로 막았습니다.

* **전송 전 검사:** 실제 키 값, 토큰 패턴, 개인정보 패턴, 비공개 데이터의 지문을 검사합니다.
* **bubblewrap 샌드박스:** OpenCode가 작업 폴더와 도구 폴더만 보도록 합니다. 홈 디렉터리와 다른 데이터는 아예 존재하지 않는 것처럼 보입니다.
* **환경변수 비우기:** 샌드박스를 만들다가 알게 됐는데, Claude 세션의 토큰이 환경변수로 OpenCode에 그대로 넘어가고 있었습니다. 지금은 필요한 변수만 다시 넣습니다.

과거 기록 전체(세션 49개, 메시지 조각 4,401개)를 로컬에서 감사한 결과 실제 유출은 없었습니다. 운이 좋았던 것이라, 샌드박스는 꼭 권합니다.

## 정리: 위임 판단표

| 작업 | 판단 |
| --- | --- |
| 많이 읽고 짧게 보고하는 조사·분석 | **위임** |
| 테스트로 확인할 수 있는 주변 코드 | **위임** (뼈대는 직접) |
| 200줄 미만, 핵심 설계, 프로토콜·상태 관리 | **직접** |
| 10줄 수준의 수정 | **직접** (명세 비용이 더 큼) |
| 비공개 데이터가 닿는 일 | **위임 금지** |

그리고 검토 비용을 줄이는 습관 세 가지입니다.

1. 명세를 템플릿으로 만듭니다(목표, 환경, 스키마, 품질 제약, 테스트 지침).
2. 테스트는 잠그기 전에 빈 모듈로 한 번 돌립니다.
3. 보고서에는 출처 표시를 강제하고, 실행 기록은 grep으로만 확인합니다.
